A tick is reachability, not visibility. It means the middleware would let the request through — not that the answer contains everybody's data. Manager routes all pass ManagerScope inside the controller, which narrows every query to that manager's own direct reports; a tick on /manager/team/{employee} still 403s for somebody else's staff. The same is true of the employee portal, which is scoped to the signed-in person.
  • ✓ — the role can reach the route.
  • — — refused, by role gate or by a missing permission.
  • public — no sign-in required at all (privacy policy, account deletion, login, the API ping).

Role gates run before permission middleware on routes inside them. That is why a manager holding approve-leave still cannot reach anything inside the role:admin|hr group — the gate refuses them first, whatever permission they hold.

!Boundaries worth stating

  • The admin app is one gate, not many. Everything under role:admin|hr is closed to managers and employees regardless of permissions. Adding |approve-leave to a route in that group advertises manager access that can never be reached.
  • Managers write in exactly one place. Approving and rejecting leave. Attendance correction is manage-attendance, roster planning is manage-shifts, exporting is export-reports — none of which the role holds.
  • HR cannot mint an administrator. Creating a login is manage-employees; granting hr or admin to one additionally needs manage-roles, which only an admin holds. The rule runs in reverse too, so HR cannot demote an existing administrator.
  • Every mobile API call needs an employee record. ApiController::employee() aborts 403 without one, so a hand-created admin signs in and then fails nearly everything.
  • Two roles are absent from this matrix by design. There is no multi-company tenancy (A2.10) and no conditional rules engine (A2.9) — access is per role and per permission, not per condition.
