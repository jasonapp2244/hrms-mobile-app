A Web setup — 9 steps

Follow in order. Steps A1–A7 put the system online; A8–A9 make it usable and safe.

A1 Domain or subdomain

Owner: IT · 10 minutes

If the company already has a domain — no purchase needed. Ask IT to create a subdomain:

  1. Open the company DNS panel
  2. Add an A record: name emp, value = the server IP address from step A2
  3. Result: emp.klutchcleaning.com — this subdomain, not another

If there is no company domain — buy one from any registrar (~$10–20/year), then point its nameservers at the host.

Allow up to 24 hours for a brand-new domain to resolve worldwide. A subdomain on an existing domain is usually live within minutes.

A2 Hosting

Owner: IT · Same day

Send this exact specification to any prospective host and require a yes to all of it:

RequirementMinimum
PHP8.2 or newer
MySQL / MariaDB5.7+ / 10.3+
PHP extensionspdo_mysql, mbstring, openssl, gd, zip, fileinfo, intl, bcmath, curl, xml, dom, iconv, tokenizer, ctype, json, exif
Free SSL from the hosting panelIncluded — confirm explicitly
Ability to set the web root to a subfolderRequired — see A3
Scheduled tasks (cron)Required — at least every 5 minutes, see A9
SSH or SFTP accessRequired — the setup commands in A6 are run over it
Automated backupsStrongly preferred

Decided: managed webspace. emp.klutchcleaning.com points at the webspace, so that is the host this guide now describes. Every feature works there and nothing is switched off, but two things behave differently from a VPS and both are worth knowing before you start:

  • Nothing runs continuously. The scheduler and the queue are driven by a scheduled task instead of a long-lived process, so a notification goes out within about five minutes rather than within a second. A9 sets this up; without it no reminder, no end-of-day close and no email ever fires.
  • Backups cannot be automatically test-restored, because that needs a spare database the plan does not provide. Dumps are still taken. Restoring one by hand — see A9 — is the only proof they read back.

A VPS ($10–40/month) reverses both, and moving to one later is a change of host rather than a change of software: the same repository, the same .env, the same commands.

A3 Upload the code and set the web root

Owner: Developer · 30 minutes

Upload the application folder via Git (preferred) or SFTP. On managed webspace the checkout goes under the account's home directory, not /var/www, which you have no rights to:

# Over SSH, from the account's home directory
git clone <repository-url> ~/emp
cd ~/emp

Then, in the hosting panel, set the document root of emp.klutchcleaning.com to the public folder inside that checkout. On webspace this is a panel setting, not a config file.

The single most important setting on this page. The document root must point at the public folder — not at the folder above it.

If it points at the application folder, anyone can open yoursite.com/.env in a browser and read your database password, application key and mail credentials in plain text. This is the most common and most damaging Laravel deployment mistake. Only the public folder should ever be reachable.

Set folder permissions so the web server can write logs and cache:

chmod -R 775 storage bootstrap/cache
No chown on webspace. There is no www-data user and no root to become; PHP already runs as the hosting account that owns the files. The chown line belongs to a VPS install and will simply fail here — that failure is expected, not a problem to solve.

A4 Create the database

Owner: Developer · 10 minutes

On managed webspace the database is created in the hosting panel, not with SQL — the account has no rights to CREATE DATABASE or CREATE USER. Create it there, and write down the three values the panel gives back: the database name, the user, and the host.

The host is usually not localhost. Managed hosting commonly puts MySQL on a separate machine with a name of its own. Copy whatever the panel shows into DB_HOST in A5; assuming 127.0.0.1 produces a connection refused that reads like a broken install.

For reference, the equivalent SQL on a host where you do have those rights is:

CREATE DATABASE emp CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'emp_user'@'localhost' IDENTIFIED BY '<strong-password>';
GRANT ALL PRIVILEGES ON emp.* TO 'emp_user'@'localhost';
FLUSH PRIVILEGES;
Do not reuse the development settings. Locally this project connects as root with no password at all. That is acceptable on a laptop and unacceptable anywhere else. Create a dedicated user with a strong password, and grant it rights to this one database only.

A6 Install dependencies and build the database

Owner: Developer · 20 minutes

On webspace, check which PHP you are running first. The command-line PHP is often an older build than the one serving the site, and is usually a versioned binary rather than plain php: 
which php8.3 || ls /usr/bin/php*
php8.3 -v && php8.3 -m | grep -E 'gd|zip|mbstring|intl|bcmath'
Substitute that binary for php in every command below, and run Composer through it (php8.3 composer.phar …) if composer is not on the path. gd and zip are what the PDF and Excel exports need; if they are missing, switch the PHP version in the panel rather than trying to install them. 
# 1 — install PHP libraries, production mode (excludes dev tools)
composer install --no-dev --optimize-autoloader

# 2 — generate a fresh application key
php artisan key:generate

# 3 — create all tables
php artisan migrate --force

# 4 — load roles and permissions ONLY (see warning below)
php artisan db:seed --class=RolePermissionSeeder

# 5 — link the public storage folder (not yet created on this project)
php artisan storage:link

# 6 — cache configuration for speed
php artisan config:cache
php artisan route:cache
php artisan view:cache
Step 4 must name the seeder class explicitly. Running the bare php artisan db:seed also runs DemoDataSeeder, which creates a live administrator account — admin@emp.test with the password password — plus fictional employees and fake attendance records. On a public server that is both a security hole and corrupted data. Use --class=RolePermissionSeeder exactly as written.

Then create your real administrator — there is no seeded account to fall back on, which is correct:

php artisan tinker
$u = \App\Models\User::create([
    'name' => 'Your Name',
    'email' => 'you@company.com',
    'password' => \Hash::make('<a strong password>'),
    'company_id' => 1,
    'is_active' => true,
]);
$u->assignRole('admin');
No front-end build step. The interface is served straight out of public/assets; there is no Vite or Tailwind pipeline to run. Node.js is not needed on the live server or on a build machine — deployment is PHP only.

A7 Enable SSL Feature-critical

Owner: IT · 15 minutes

  1. In the hosting panel, find SSL / TLS or Let's Encrypt
  2. Issue a certificate for your domain — usually one click, free
  3. Enable Force HTTPS so plain HTTP redirects automatically
  4. Confirm the padlock appears in the browser
This is not a security nicety on this project — it is a functional requirement. Browsers refuse to release GPS coordinates over an unencrypted connection, as a hard rule that cannot be overridden by any setting on our side. Without SSL, the check-in button will fail to capture location for every employee, and the system's primary feature simply does not work.

Verify properly: open the site on a phone, log in as an employee, press check-in, and confirm a latitude and longitude appear on the record. Seeing the padlock is not sufficient proof on its own.

A8 Connect email Currently sends nothing

Owner: IT + Developer · 1 hour

The project is set to MAIL_MAILER=log, meaning every message is written to a file and none has ever been delivered. Choose one route:

If the company hasHostPortCredentials
Google Workspacesmtp.gmail.com587An App Password, not the account password
Microsoft 365smtp.office365.com587Mailbox credentials
Neithersmtp-relay.brevo.com587Brevo login + generated SMTP key

Replace the mail block in .env:

MAIL_MAILER=smtp
MAIL_SCHEME=smtp
MAIL_HOST=smtp-relay.brevo.com
MAIL_PORT=587
MAIL_USERNAME=<your-login>
MAIL_PASSWORD=<your-smtp-key>
MAIL_FROM_ADDRESS="hr@company.com"
MAIL_FROM_NAME="Employment Management Portal"
This project runs Laravel 12, which uses MAIL_SCHEME, not MAIL_ENCRYPTION. Older guides found online will tell you to set MAIL_ENCRYPTION=tls — that key is ignored here. Use MAIL_SCHEME=smtp for port 587, or smtps for port 465.

Clear the cache and send a test:

php artisan config:clear
php artisan tinker
Mail::raw('Test from Employment Management Portal', fn($m) => $m->to('you@company.com')->subject('Test'));

Then add DNS records, or your mail will be filed as spam regardless of correct settings. The provider supplies the exact values; IT adds them to the domain:

RecordPurpose
SPFDeclares which servers may send mail for your domain
DKIMCryptographically signs each message as genuinely yours
DMARCTells receivers what to do with mail failing the above
This is the highest-value hour on the whole list. Features that are already built and paid for are currently inert purely because no sending service is configured. Nothing needs to be developed — only connected.

A9 Background jobs, backups and branding Nothing runs without this

Owner: IT + Marketing · 1 hour

Background jobs. Two scheduled tasks drive everything that is not a click: the check-out reminders, the end-of-day close, leave accrual, document-expiry warnings, the nightly backup, the scheduled reports, and the delivery of every email and push notification. Add both through the panel's cron manager. The exact entries, with the reasoning behind each flag, are in deploy/emp-webspace.cron:

# APP = the directory containing artisan; PHP = the CLI binary from A6
*/5 * * * *    cd $APP && $PHP artisan schedule:run >> storage/logs/scheduler.log 2>&1
1-56/5 * * * * cd $APP && $PHP artisan queue:work --stop-when-empty --max-time=50 --tries=3 --backoff=10,60,300 >> storage/logs/queue.log 2>&1
Without these two entries the dashboard looks completely correct and none of it happens. Attendance is never closed, no reminder is sent, no backup is taken, and a leave decision never reaches the employee. There is no error anywhere — the work simply queues up and waits. This is the single easiest thing to skip on this page.

Two details are not arbitrary. The scheduler runs every five minutes because the platform will not repeat a job more often, and every scheduled task in this project already falls on a five-minute boundary, so nothing is missed. The queue entry carries --max-time=50 because the platform kills any run still going at 60 seconds; the worker retires at 50 and the next run continues, whereas being killed mid-job leaves that job reserved until it times out. The queue is offset by a minute so the two never start in the same second.

Backups. Once the scheduler above is running, the nightly database backup is already part of it — it fires at 02:10 with no separate crontab entry. If the host also provides its own automated backups, enable those too and confirm the schedule.

On webspace the backup is taken but not proved. On a server, db:backup --verify restores each dump into a scratch database to confirm it reads back. This account cannot create one, so the command degrades to a warning and you get dumps without the proof. Restore one by hand into any database you can create, before go-live, and confirm the attendance records are present and readable. An untested backup is a hope, not a safeguard, and this is a system payroll is calculated from.

Branding. Replace the placeholder logo with the company's own so exported PDF reports look official. Supply an SVG or transparent PNG, plus a square version for small spaces.

B Mobile setup — 6 steps

The app and its API are built. What is left is the paperwork of publishing: the accounts, the signing keys and the store listings. B3 has a two-week external wait and depends on nothing we build, so start it first.

The API exists. routes/api.php serves the endpoints under /api/v1, Laravel Sanctum issues the tokens, and every endpoint is written up in API-Reference_v1.md. The Flutter client is in mobile/. Nothing in B is waiting on development work.
The API address is compiled into the app, not configured at runtime. A build made against the wrong address cannot be pointed at the right one afterwards — it has to be rebuilt and resubmitted, which on iOS means another review. Build against the live address: 
flutter build appbundle --dart-define=API_BASE=https://emp.klutchcleaning.com/api/v1
flutter build ipa       --dart-define=API_BASE=https://emp.klutchcleaning.com/api/v1
The default is the Android emulator's address for a laptop, which is why a release build with no --dart-define installs cleanly and then hangs on the login screen with no error.
Every mobile sign-in needs an employee record. The API resolves the caller to a row in employees and returns 403 "No employee record is linked to this account" when there is none. A hand-created administrator has no employee row, so it signs in and then fails on nearly every screen — link the account from the employee's own page under Sign-in Account before testing.

B1 Company Google account Do this first

Owner: IT · 15 minutes · Free

One account covers three separate services, so this decision is made once and is awkward to reverse:

company Google account  (e.g. it@company.com)
   ├── Google Play Console   → publishing the Android app
   ├── Firebase              → push notifications
   └── Google Maps Platform  → optional embedded maps
Never register under a personal Gmail address. When that person leaves the company, the organisation loses control of its own app store listing, and recovery is slow and sometimes impossible. Use a shared company address with the password held in the company password manager. This is the most common avoidable failure in mobile projects.

B2 Google Play Console $25 once

Owner: IT · 1–3 days

  1. Go to play.google.com/console and sign in with the B1 account
  2. Choose Organisation, not personal
  3. Pay the $25 one-time fee — lifetime, no renewal
  4. Complete identity verification (company documents required)
  5. Verify the developer contact address

Without this, the app can only be distributed as an installer file, which gives no automatic updates and is blocked by policy on most managed devices.

B3 Apple Developer Program Start now — 2 week wait

Owner: IT · 1–2 weeks · $99/year

  1. Obtain a D-U-N-S number first if the company has none — request free at the Dun & Bradstreet site. This alone takes up to a week and is the usual cause of delay.
  2. Create a company Apple ID — again, never personal
  3. Enrol at developer.apple.com/programs as an Organisation
  4. Apple verifies the company independently, sometimes by telephone
  5. Pay $99; renews annually
This is the longest lead time in the entire project and it depends on nothing we build. If an iPhone app is even possible, start enrolment today. Starting early costs $99. Starting late costs a two-week delay to launch, with the finished app sitting idle. If the membership later lapses, the app is removed from the store.

B4 Firebase — push notifications Free

Owner: Developer · 1 hour

  1. Go to console.firebase.google.com, signed in with the B1 account
  2. Add project — name it after the company
  3. Add an Android app; download google-services.json
  4. Add an iOS app; download GoogleService-Info.plist
  5. For iOS, generate an APNs key in the Apple Developer account (B3) and upload it to Firebase
  6. Under Project settings → Service accounts, generate a private key and save the JSON file to storage/app/firebase/service-account.json, then set FCM_ENABLED=true and FCM_PROJECT_ID in .env and run php artisan config:clear
Not the legacy Server Key. Sending uses FCM's v1 API, which authenticates with that service-account JSON — the old server key does not work and is being retired by Google. The file is a credential: anyone holding it can notify every installation of the app, so it stays out of the web root, out of git, and out of email. Push-Notifications_Setup.md has the full procedure.

Free at any volume this project will reach. Without it the app only informs staff when they happen to open it, which removes most of the advantage of an app over the website.

Push is queued, like email. It is delivered by the same scheduled task as everything else, so on this host a notification arrives within about five minutes and nothing arrives at all until A9 is done.

B5 App signing keys Irreplaceable

Owner: Developer generates · IT holds · Free

keytool -genkey -v -keystore hrms-release.keystore \
  -alias hrms -keyalg RSA -keysize 2048 -validity 10000
If this key is lost, the Android app can never be updated again. Not delayed — never. The only remedy is publishing a completely new listing and asking every employee to uninstall and reinstall, losing all installs and history. Projects have died on this.

Required custody: store the keystore file and its password in the company password manager, held by IT rather than any individual developer, with a second copy in a separate secure location. Additionally enable Play App Signing at first upload so Google retains a recoverable backup — take this option.

One known defect remains before real payroll depends on this system. Employee records still have no soft delete, so a deletion is permanent. The data-loss risk it carried has been closed — an employee with attendance history can no longer be deleted at all, because doing so used to cascade away every punch behind them; they are set to Terminated instead. Three of the four have been fixed: new employees can now be given a login from their own page, the password form is rate limited, and attendance history can no longer be destroyed by a deletion.
